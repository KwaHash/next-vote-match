# 選挙データ収集戦略

> **決定事項**: 全選挙をスクレイピングするのではなく、3段階の優先度で段階的に展開する。  
> **版**: 2026-06-25

---

## 問題の整理

日本の選挙数（年間目安）:

| 種別 | 年間件数目安 | 候補者数/件 | 管理難度 |
|---|---|---|---|
| 衆議院議員選挙 | 0〜1回 | 〜1,000人 | ★（国政・大手メディア注目） |
| 参議院議員選挙 | 1回（3年に1回・半数改選） | 〜400人 | ★ |
| 都道府県知事選挙 | 年間10〜15件 | 2〜8人/件 | ★★ |
| 政令市長選挙 | 年間4〜6件 | 2〜6人/件 | ★★ |
| 都道府県議会議員選挙 | 年間延べ50件以上 | 多数 | ★★★★ |
| 市区町村長・議会選挙 | 年間500件以上 | 膨大 | ★★★★★ |

**結論: 市区町村議会選挙まで全スクレイピングするのは現実的でない。**

---

## 推奨: 3段階展開モデル

### Tier A — 国政選挙（Phase 1: 優先実装）

対象: 衆議院・参議院選挙

| 項目 | 内容 |
|---|---|
| 年間件数 | 1〜2回 |
| 候補者数 | 衆議院: 約1,000人 / 参議院: 約400人（半数改選） |
| データ取得方法 | ① 候補者がプレミアムプランで直接入力（メイン） <br> ② 政党公式サイトから告示後に半自動取込 <br> ③ 総務省・NHK選挙データとの連携 |
| スクレイピング | **不要**（候補者本人入力 + 政党連携） |
| 注目度 | 最高（集客コンテンツとして最大効果） |

**実装方針:**
- 衆議院選挙の選挙区データは現在 `representatives2026` テーブルに保有済み
- 告示後 72 時間以内に候補者情報を掲載できる体制を整える
- 候補者本人がプレミアムプランで詳細を追記できる（SNS・写真・公約等）

---

### Tier B — 首長選挙（Phase 2: 3〜6ヶ月後）

対象: 都道府県知事選挙 + 政令市長選挙（20都市）

| 項目 | 内容 |
|---|---|
| 年間件数 | 知事: 10〜15件 / 政令市長: 4〜6件 |
| 候補者数 | 各2〜8人（少数で管理しやすい） |
| データ取得方法 | 告示後に各選管サイトから手動＋半自動取込 |
| スクレイピング | **選管サイトのみ（告示後の公開データ）** |
| 注目度 | 高（地元民の関心が高く、SNS拡散しやすい） |

**政令市 20都市（対象）**:
札幌・仙台・さいたま・千葉・横浜・川崎・相模原・新潟・静岡・浜松・
名古屋・京都・大阪・堺・神戸・岡山・広島・北九州・福岡・熊本

**実装方針:**
- 選管サイトは robots.txt を必ず確認してからスクレイピング
- 告示日の翌日に手動チェック → 管理画面から登録
- 候補者への通知（「seijiselect.jp に掲載されました」メール）

---

### Tier C — 都道府県議会・市区町村（Phase 3: 1年以降）

対象: 都道府県議会議員選挙・中核市以上の市議会

| 項目 | 内容 |
|---|---|
| 件数・候補者数 | 膨大（全国で年間5,000候補者超） |
| データ取得方法 | ① 候補者自身がプレミアム登録 <br> ② 自治体オープンデータ（整備が進んだ場合） <br> ③ 市民ボランティアによるデータ入力 |
| スクレイピング | **原則なし**（コスト・法的リスクが高すぎる） |

**実装方針:**
- 候補者自身が登録するモデルに移行（プレミアム月額で十分なインセンティブ）
- 地域ごとに「候補者データ収集ボランティア」を募集（Wikipedia型コミュニティ）
- 政府の選挙オープンデータ整備（2027年頃）を待って連携

## スクレイピングの法的・技術的リスク

### やってはいけないこと

| NG行為 | 理由 |
|---|---|
| 民間選挙情報サイト（選挙ドットコム等）のスクレイピング | 著作権・利用規約違反リスク |
| 政党の候補者一覧を無断で大量取得 | 利用規約確認が必要 |
| 個人の公式サイトを高頻度クロール | DoS攻撃と見なされうる |
| SNS フォロワー数・投稿の無断大量取得 | 各API利用規約違反 |

### やっていいこと（確認が必要）

| 行為 | 注意点 |
|---|---|
| 総務省・選管サイトの公開データ取得 | 利用規約確認。robots.txt 遵守。間隔 5秒以上 |
| 候補者の公式Webサイトのリンク収集 | 公開情報の参照はOK |
| YouTube Data API でのチャンネル情報取得 | APIキーと利用規制を遵守 |
| Twitter/X API での公開ツイート取得 | 有料プラン（Basic $100/月〜）が必要 |

## SNS データ収集戦略

### 各プラットフォームの実現可能性

| プラットフォーム | API | 費用 | 取得できる情報 | 推奨 |
|---|---|---|---|---|
| **YouTube** | Data API v3 | 無料（10,000units/日） | チャンネル登録者数、動画一覧、再生回数 | ✅ Phase 1から実装 |
| **X（旧Twitter）** | Basic API | $100/月 | ツイート、フォロワー数、エンゲージメント | △ Phase 2以降 |
| **Facebook** | Graph API | 無料（ページのみ） | フォロワー数、投稿（ページのみ） | △ 政治家の公式ページのみ |
| **Instagram** | Graph API | 無料（ビジネスアカウントのみ） | 投稿、フォロワー（本人認証必要） | ✅ 候補者本人登録後 |
| **TikTok** | Research API | 無料（申請制） | 動画、再生回数 | △ 将来検討 |
| **LINE** | Messaging API | 無料（送信数制限あり） | 友達数は非公開 | ❌ 取得不可 |

### Phase 1 で実装するSNS機能

```
候補者詳細ページに以下を表示:
1. SNSリンク一覧（YouTube・X・Facebook・Instagram等）
2. YouTube: 直近3本の動画埋め込み（YouTube oEmbed, 無料）
3. X: 最新ツイート埋め込み（oembed API, 無料）
4. フォロワー数: 候補者が手動入力 or 管理者が定期更新
5. 活動スコア: 投稿頻度を「高・中・低」で表示（管理者判断）
```

## データ更新フロー（本番運用）

```
選挙告示
  ↓（翌日）
管理画面から候補者データ登録（手動 or CSV一括）
  ↓
候補者に「掲載開始」通知メール送信
  ↓
候補者がプレミアムプランに登録 → 自分でSNS・写真・公約を入力
  ↓（毎日）
YouTube API で登録者数・最新動画を自動更新（バッチ処理）
  ↓（選挙翌日）
開票結果を管理画面で更新
```
